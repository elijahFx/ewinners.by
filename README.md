# E-Winners — личный кабинет и админка

Платформа для учёта баланса клиентов call-центра / CRM: счета, документы, операции, API-ключи и банковский контроль.

```
ewinners.by/
  ewinners.by/   # фронтенд (React + Vite) → Netlify
  server/        # бэкенд (Express + MySQL)
```

---

## Быстрый старт

### Фронтенд

```bash
cd ewinners.by
npm install
npm run dev        # локально
npm run build      # прод-сборка
```

Переменная `VITE_API_URL` — адрес API (по умолчанию прод/стенд).

### Бэкенд

```bash
cd server
cp .env.example .env   # если есть пример; иначе заполните .env
npm install
npm run migrate
npm run seed           # справочники + админ eadmin
npm start
```

Полезные команды:

| Команда | Назначение |
|--------|------------|
| `npm run migrate` | Миграции БД |
| `npm run seed` | Услуги, тарифы, админ `eadmin` |
| `npm run reset:handoff` | Очистка пользователей/клиентов + админ `eadmin` |
| `npm run create:techadmin` | Аккаунт `techadmin` |
| `npm run create:admin -- <логин> <пароль> [ФИО]` | Создать/обновить админа |

Создание произвольного админа:

```bash
cd server
npm run create:admin -- pavel 12345678910 "Павел"
```

Команду можно запускать повторно: у существующего логина сбросится пароль,
подтвердится роль `admin`, а старые сессии станут недействительными
(`token_version` увеличивается).

Админ по умолчанию после seed / reset:

- логин: `eadmin`
- пароль: `tobeornottobe2077`

На странице входа можно указать **логин или email**.

Технический админ:

```bash
npm run create:techadmin
```

- логин: `techadmin`
- пароль: `tobeornottobe2001`

## Роли

| Роль | Кто это | Что может |
|------|---------|-----------|
| **admin** | Администратор | Всё: клиенты, пользователи, счета, банкинг, корректировки |
| **accountant** | Бухгалтер | Счета, банкинг, корректировки, просмотр |
| **client** | Клиент | Свой кабинет: баланс, счета, документы, операции, CRM |

## Как работать администратору

### 1. Создать компанию (организацию)

1. Войти как admin / accountant.
2. Раздел **Клиенты** (`/cabinet/admin/companies`).
3. Создать компанию: название, УНП, адрес, банк, IBAN, БИК и т.д.

Организации создаёт **только админ**. Клиент сам их добавить не может.

### 2. Создать пользователя-клиента

1. Раздел **Пользователи**.
2. **Добавить**: email, ФИО, роль `client`.
3. Можно сразу указать основную организацию.
4. Режим пароля: приглашение на email / автопароль / ручной.

### 3. Привязать несколько организаций к одному пользователю

1. В таблице пользователей у клиента нажать **Орг.**
2. Выбрать компанию из списка (сначала создайте её в **Клиенты**).
3. **Привязать**.
4. При необходимости привяжите ещё компании.
5. **Отвязать** — убрать доступ к организации.

В кабинете клиента в сайдбаре появится переключатель **Организация**. Баланс, счета и документы относятся к **активной** организации.

### 4. Счета клиентов

Раздел **Счета** (`/cabinet/admin/invoices`):

- все счета всех организаций;
- просмотр / скачивание PDF;
- кнопка **Оплачен** — отмечает счёт оплаченным и **зачисляет сумму на баланс** клиента. Акт по счёту не формируется: акт оказанных услуг создаётся автоматически по итогам месяца и отражает только списания с баланса.
- **Удаление оплаченного счёта** доступно только администратору. Если оплата подтверждена вручную, зачисление отменяется и баланс уменьшается на сумму зачисления; если к счёту привязан реальный банковский платёж, баланс не корректируется — удаляется только счёт.

### 5. Банкинг

Раздел **Банкинг** — поступления / списания / выписка из **MTBank Open API** (через AvTunProxy).

Нужны в `server/.env`: `MTBANK_API_KEY`, `MTBANK_CONSENT_ID`, при необходимости `MTBANK_ACCOUNT_ID` / `MTBANK_ACCOUNT_IBAN`, `MTBANK_PROXY=http://127.0.0.1:10224`.

Если MTBank выдал несколько согласий (например, отдельно на КЦ и на HR/Digital), перечислите их в `MTBANK_CONSENT_IDS` через запятую. `MTBANK_CONSENT_ID` остаётся основным, а счета из всех согласий объединяются: каждый запрос к банку идёт со своим `X-accountConsentId`.

PHP-cron каждые 2 минуты: `server/cron/mtbank_check_payments.php` → `/api/internal/bank/sync` — если в назначении платежа есть номер счёта (`EW-…`) и сумма совпадает, счёт помечается оплаченным.

Автосинк не создаёт дубли: платёж ищется по `external_id`, а если банк вернул новый reference — по отпечатку «сумма + дата операции + плательщик + назначение». Если счёт уже оплачен вручную, банковский платёж привязывается к нему и помечается `credited` без повторного зачисления. Дополнительно синк всегда запрашивает свежий 3-дневный хвост: длинный период MTBank иногда отдаёт без только что поступивших платежей. Старые дубли можно почистить: `cd server && npm run bank:dedupe` (предпросмотр), `npm run bank:dedupe -- --apply` (выполнить; перед этим создаётся JSON-бэкап).

Рабочее место направления (`/cabinet/admin/direction/hr|digital|kc`) показывает остаток, поступления и расходы по счёту направления из MTBank. Счета направлений заданы в `server/src/services/accounts.js` и переопределяются через `ACCOUNT_IBAN_HR`, `ACCOUNT_IBAN_DIGITAL`, `ACCOUNT_IBAN_KC`; IBAN должен совпадать со счётом из согласия `MTBANK_CONSENT_ID`.

Страница **Банкинг** следует за выбранным направлением: счёт, поступления/списания и CSV-выписка относятся к счёту HR, Digital или КЦ. Если счёт направления не входит в согласие MTBank, страница показывает предупреждение вместо данных другого счёта.

В HR/Digital сайдбар показывает только **Админ-обзор** (админам), **Рабочее место**, **Банкинг** (админам) и **Клиентов** этого направления; глобальные разделы КЦ (почта, пользователи, счета, документы и т.д.) скрыты и недоступны по прямой ссылке. HR-сотрудник видит только **Рабочее место HR**: переключатель направлений скрыт, а API принудительно возвращает только HR (клиенты, счета, банк, документы). На рабочем месте направления вместо списка клиентов показываются счета этого направления; кнопка «Оплачен» доступна админу/бухгалтеру. Клиенты фильтруются по `companies.direction`; направление меняется в карточке клиента.

### 6. Корректировки баланса

Раздел **Корректировки** — ручное зачисление / списание с комментарием (без привязки к счёту).

### 7. API-ключи CRM

Раздел **API-ключи** — ключи компаний для интеграции CRM. Клиент также может сгенерировать ключ у себя в **Интеграция CRM**.

SalesRender (списание при статусе «Вручено»): см. `server/docs/SALESRENDER.md`.  
`POST /api/crm/salesrender/delivered` + `X-Api-Key` компании.

### 8. Остановка проектов SalesRender и пограничная зона

Если списание не проходит из-за баланса или кредитного лимита, вебхук больше не возвращает ошибку: заказ попадает в `salesrender_pending_charges` и SalesRender получает `200 { queued: true }`. Проект клиента при этом архивируется в SalesRender (`projectMutation.updateProject({ archived: true })`) — новые заказы создать нельзя, а уже созданные остаются у менеджеров. После пополнения очередь разбирается по порядку; проект остаётся остановленным, пока в очереди есть неоплаченный заказ.

Порог: `available = balance + credit_limit` для `allow_credit`, блокировка при `available <= 0`; `allow_debt` не блокируется; `min_balance` пока не используется.

Состояние хранится в `company_financial_state`, `salesrender_project_state` (только наши архивации) и `salesrender_pending_charges`. Раздел **Сверка** показывает пограничную зону и остановленных клиентов, позволяет списать/отменить заказ и пересчитать состояние.

По умолчанию включён безопасный режим `SALESRENDER_CONTROL_DRY_RUN=1`: состояние считается и пишется в БД, но реальные проекты не архивируются. Для боевого режима: `SALESRENDER_CONTROL_DRY_RUN=0` и перезапуск `ewinners-api`. Первым под остановку попадает клиент `id 14` (баланс `-345`, лимит `300`, проект SalesRender `5`) — включать боевой режим только после подтверждения.

## Как пользоваться кабинетом клиента

1. Войти по логину (email / логин) и паролю.
2. Если организаций несколько — выбрать нужную в сайдбаре.
3. Основные разделы:

| Раздел | Назначение |
|--------|------------|
| **Обзор** | Баланс, краткая сводка |
| **Операции** | История списаний / пополнений, экспорт в Excel |
| **Счета** | Создать счёт на пополнение, скачать PDF |
| **Документы** | Счета, акты (автоматически за месяц), детализация; «Сформировать детализацию» |
| **Тарифы** | Актуальные тарифы |
| **Организации** | Просмотр и переключение (без создания) |
| **Уведомления** | Email / Telegram |
| **Интеграция CRM** | API-ключ и документация endpoints |

### Пополнение баланса

1. **Счета** → указать сумму → сформировать PDF.
2. Оплатить по реквизитам.
3. Админ в **Счета** отмечает счёт **Оплачен** → баланс увеличивается. Акт появится в **Документах** после окончания месяца.

### Акты оказанных услуг

- Счёт — это пополнение баланса. Акт — это **только те деньги, которые списаны с баланса** за календарный месяц.
- Акт формируется автоматически: в последний день месяца в 23:50 (Минск), а на следующий день обновляется с учётом последних списаний. Если за месяц списаний не было, акт не создаётся.
- В акте по КЦ указано: «Акт составлен в связи с оказанием услуг по обработке заявок». Формулировки — только про оказание услуг.
- В акте услуги обзвона называются «Заказы с повышением чека» и «Заказы без повышения чека» — без внутренних терминов «апсейл/кроссейл».
- Клиент не может сформировать произвольный акт: сумму и услуги выбрать нельзя. Но в **Документах** есть кнопка **«Запросить акт за месяц»**: она собирает акт только по фактическим списаниям с баланса за выбранный прошедший месяц. Повторный запрос открывает уже готовый документ.
- Старый маршрут акта по счёту (`/api/cabinet/invoices/:id/act`) отвечает отказом: акт по счёту больше не формируется.
- Управление планировщиком: `MONTHLY_ACT_ENABLED=0`, `MONTHLY_ACT_HOUR`, `MONTHLY_ACT_MINUTE`, `MONTHLY_ACT_BACKFILL=0`.
- Ручной пересчёт/досоздание: `cd server && npm run acts:generate -- --period=2026-10` (или `--company=<id>`, `--force`).
- Досоздание за все прошедшие месяцы со списаниями: `cd server && npm run acts:generate -- --all-past` (уведомления клиентам не отправляются).

### Детализация

В **Документы** → **Сформировать детализацию**.  
За один календарный месяц одна детализация: повторное нажатие **обновляет** тот же PDF (на экране будет сообщение). Если списаний не было — документ с суммой 0.00.

## Типовой сценарий «с нуля»

1. Админ создаёт компанию в **Клиенты**.
2. Админ создаёт пользователя `client` в **Пользователи**.
3. Админ жмёт **Орг.** у пользователя и привязывает одну или несколько компаний.
4. Клиент входит, выбирает организацию, выставляет счёт.
5. Админ подтверждает оплату счёта → клиент тратит баланс через CRM / тарифы.

## Замечания по продакшену

- Заполните `.env` сервера: БД, JWT, SMTP, реквизиты компании для счетов, MTBank (`MTBANK_API_KEY` и согласие) и Telegram.
- Шрифт с кириллицей для PDF: `server/assets/fonts/ArialUnicode.ttf` (или DejaVu).
- После деплоя бэкенда перезапустите Node-процесс, чтобы подтянуть новые маршруты.
